означает:

👉 systemd-сервис gitlab-runner уже создан

✅ ПРАВИЛЬНОЕ РЕШЕНИЕ (БЕЗ СНОСА)

🔹 ШАГ 1. Посмотрим, под кем сервис СЕЙЧАС
sudo systemctl cat gitlab-runner


Обрати внимание на строку вида:

User=...


Очень вероятно:

либо User=root

либо строки User= вообще нет

🔹 ШАГ 2. ПРАВИЛЬНО ПЕРЕОПРЕДЕЛЯЕМ ПОЛЬЗОВАТЕЛЯ

Создаём override-файл systemd (это best practice).

sudo systemctl edit gitlab-runner


Откроется редактор. Вставь ТОЛЬКО ЭТО:

[Service]
User=gitlab-runner
Group=gitlab-runner


Сохрани и выйди.

📌 Это не правка системного файла, а корректное расширение.

🔹 ШАГ 3. Перечитываем systemd и перезапускаем сервис
sudo systemctl daemon-reexec
sudo systemctl daemon-reload
sudo systemctl restart gitlab-runner


Проверка:

sudo systemctl status gitlab-runner


Должно быть:

Active: active (running)

СКРИНШОТ ПРО ОШИБКУ ДОБАЛВЕНИЯ КЛЮЧА


You can't put a raw private SSH key into a masked GitLab CI/CD variable because of characters like /, +, and especially whitespace (spaces, newlines) that GitLab's masking regex rejects, but the standard solution is to base64 encode the key, store the single-line encoded string in GitLab, and then decode it within your gitlab-ci.yml script to use it. You can use cat ~/.ssh/id_rsa | base64 -w0 to encode and echo "$VAR" | base64 -d in your pipeline to decode. 
Why it fails
Masking Rules: GitLab's masking (to hide secrets in logs) has strict rules, often requiring alphanumeric characters plus specific symbols (@, :, ., ~) and disallowing whitespace and newlines.
SSH Key Format: Private keys have -----BEGIN OPENSSH PRIVATE KEY----- (or similar) headers, newlines, and spaces, violating these rules. 
The Solution: Base64 Encoding
Encode the Key (Local Machine):
bash

cat ~/.ssh/id_rsa | base64 -w0

Выводили мой ключ:
mburmistrov@runner-region-d:~$ cat ~/.ssh/gitlab_runner_to_deploy | base64 -w0

Вставляем его в Гитлаб, сохраняем

🔹 Как Docker формирует файловую систему контейнера

Когда контейнер стартует, порядок такой:

Берётся файловая система image

Затем поверх неё монтируются volumes

Если volume смонтирован в существующий путь —
👉 содержимое image в этом месте становится невидимым

🔹 Почему /etc/hosts «очищается» в Yandex Cloud

Это нормальное поведение YC:

/etc/hosts генерируется cloud-init

При reboot → файл пересоздаётся

Все ручные правки удаляются

📌 Это не баг, это фича.

🔹 Почему быстрый фикс через /etc/hosts плох
Подход	Минус
Править вручную	Не воспроизводимо
Скрипты с проверками	Избыточно
Cloud-init override	Сложно для диплома
✅ ПРАВИЛЬНОЕ РЕШЕНИЕ (И ТЫ ЕГО УЖЕ ИСПОЛЬЗУЕШЬ)
👉 extra_hosts в config.toml runner’а
[runners.docker]
  extra_hosts = [
    "registry.internal:10.130.0.7"
  ]

Почему это идеально

✔ Работает только там, где нужно
✔ Не зависит от /etc/hosts хоста
✔ Не ломается при reboot
✔ Не требует DNS
✔ Документируемо
✔ Production-grade

📌 Ключевая идея (одной строкой)

Docker volume ВСЕГДА имеет приоритет над содержимым образа.

🔹 Как Docker формирует файловую систему контейнера

Когда контейнер стартует, порядок такой:

Берётся файловая система image

Затем поверх неё монтируются volumes

Если volume смонтирован в существующий путь —
👉 содержимое image в этом месте становится невидимым

🔹 Что было у тебя изначально
Dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html


✔ Образ содержит правильный index.html

docker-compose.yml (СТАРЫЙ)
services:
  nginx:
    image: registry.internal:5000/test/nginx:latest
    volumes:
      - ./html:/usr/share/nginx/html

🔥 Что реально происходило при запуске
Image:
  /usr/share/nginx/html/index.html   ← НОВЫЙ (из Git)

Volume:
  ./html/index.html                  ← СТАРЫЙ (на VM4)


📌 Docker делает так:

/usr/share/nginx/html   ← ПОЛНОСТЬЮ ЗАМЕНЁН volume

Итог:

Файл из image есть

Но Docker его не показывает

Nginx читает локальный файл на VM

CI/CD «работает», но сайт не меняется

❌ Почему это особенно коварная ошибка
Симптом	Реальность
Pipeline зелёный	Да
Docker image обновляется	Да
docker pull работает	Да
Сайт обновляется	❌ Нет
Ошибок нет	❌

📌 Это классический production-антипаттерн.
